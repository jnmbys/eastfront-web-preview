## Authorized DTO
`model.battleSummaries` is opt-in and independent of `model.combat`/canAct. Envelope: matchId, core viewerControllerId, entries, olderOmitted. Each entry: battleId, accepted match revision, stage, targetHex, true resolution (independent dice, sum, CRT and CRT requirements), aggregate baseOdds / finalShift / finalCRTColumnLabel, pending kind, executed own-unit consequences and truncation flag.

Eligibility: existing controller assignment AND existing disclosedBattles membership AND participating side. No observer seat or new observation capability. Summary permission does not authorize an Action. Attackers and defenders receive their own detached archive even while model.combat is null. Outsiders fail existing membership checks before query/snapshot.

Privacy: participant IDs, strengths, remaining steps, artillery/HQ/support IDs, individual support modifiers, hidden positions and full routes are not fields of this DTO. Aggregate CRT column shifts are not dice modifiers. Per-unit consequences are conservatively limited to OWN units because the existing code establishes transient enemy animation visibility, not durable opponent route/identity ledger permission. Any enemy detail would require a separate visibility decision. No new privacy policy is inferred from disappearance or map diffs.

Actual consequences are recorded from accepted UnitStepLost, UnitRetreated, UnitAdvanced and UnitBrokeThrough Core events. One UnitStepLost is exactly one applied loss step (including its final destruction step); UnitDestroyed is not double-counted. Travel endpoints come directly from the accepted event; no inferred route. Battle stages/results use the accepted transaction's explicit allowlist. Parent battle updates include sourceBattleId. Records are made at acceptance time, not rebuilt from present hidden state when history is opened. No complete Core object/log is transmitted.

Limits: 32 battle records per match/recipient; 64 own-unit consequence entries per battle. Eviction and truncation are explicitly labelled. Routes are not stored. The maximum-shape DTO size test stays below 500 KB (within the existing 2 MB message gate alongside current production snapshots). Archive has the existing in-memory match lifetime; server restart persistence is not added. Existing server memory/reconnect constraints remain.

## Compatibility and recovery
Old snapshot decoders use an exact model-key allowlist; blindly adding a field would break them. Existing WELCOME consumption accepts extra fields, verified with retained actual legacy clients. Server advertises `battleSummary:1` on WELCOME; new clients opt in using optional `battleSummary:1` on the existing SET_SNAPSHOT_FORMAT request. ACK payload stays exactly `{format}`. No opt-in means no new model field. v1/v2/v3 unchanged, default v2 and explicit v3 unchanged. New clients on old servers see no advertisement and retain existing behavior. Post-reconnect opt-in sends one full resync containing the recipient archive; existing ordering and application paths are retained.

New snapshots validate summaries (including scope, revision, exact shapes, dice arithmetic, enums and size bounds) before any application. Invalid summaries use the existing one-full-recovery path and terminal failure if persistent. Queries also validate the optional summary before application. No new ACK, action or game state semantics.

Frontend: reuse existing card/history; show waiting before authority; only live combat events animate once. Later summary revisions update facts/pending without reroll. Earlier per-battle revisions are ignored. Reconnect/bootstrap/history are static. Caches are per session/viewer and clear on a changed match ID, bounded for summary-fed multiplayer. Nondecision pending text explicitly says wait for the authorized player. Old server/local models still use the accepted COMBAT-UX3 fallback, accurately showing the data gap.
