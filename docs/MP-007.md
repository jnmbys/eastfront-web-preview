# MP-007｜多人同步延迟专项分析

日期：2026-10-02。任务：网络优化 Worker。交付为只读诊断、测量工具和分析建议；未部署、未更改同步协议或默认 snapshot 格式。

## 结论与证据强度

**最大可观察等待区间仍是 Client Send → Client Receive，尤其是权威 snapshot 到达浏览器回调之前。当前证据不足以将 iPad/Safari 的这段等待进一步认定为纯网络、Render 计算或浏览器调度。** 本次补齐服务器阶段记录，解决此前无法拆分的问题；没有把本机结果当作真机根因。

历史公开网络的 MP-005B v2 组（Cloud Chrome，10 次部署）中位数为：发送→snapshot 535.25 ms，解析 0.65 ms，验证/重建 4.10 ms，session 应用 26.75 ms，发送→控件就绪代理 571.20 ms。不同指标的中位数不能直接相加。该测试不是 iPad，且不是本次新测试，见 [MP-005B 发布报告](../evidence/mp-005b/RELEASE-REPORT.md)。更早 MP-004 的压缩测试也未证明公开延迟改善。

本次本机 Node 双客户端采样显示服务器关键路径约 16–17 ms；它在低延迟 loopback 中占主导，但不能解释用户的秒级等待。v3 减小数据量，同时增加客户端重建成本。本机 v2/v3 发送→session 就绪均约 23 ms，不能宣称压缩已解决真实等待。

物理 iPad/Safari、当前线上服务器阶段及浏览器 paint：**未测量**。因此交付的是可执行的归因链和有证据边界的优化顺序，不是“真机根因已确认”或“延迟已降低”的结论。

## 完整延迟链

```text
Input（同步 click/keydown；自动动作可能没有）
  → NetworkPlayerSession.submit 入口
  → Client Send（JSON 已序列化，调用 WebSocket.send）
  → Server Receive（ws message 回调）
  → 请求解析/权限/revision/去重/validate
  → Core Apply 边界（原有 dispatchGameAction）
  → 授权事件与战报处理 → ACTION_ACCEPTED
  → 各接收方 Snapshot Build → Encode → JSON.stringify
  → Network Send（ws.send 调用；另记本机 write callback）
  → Client Receive（原生 message 监听回调；完整消息已交付）
  → JSON/envelope/字节限制 → 验证 → 独立副本重建
  → session apply / 同步 UI 回调
  → UI Ready（ready / interactive / syncing 采样）
```

`core-apply` 测的是 **dispatchGameAction 调用边界**，包含 Core apply、完整性检查、knowledge 和适配层工作，不是 Core 引擎纯 CPU。它嵌套在 `apply-intent` 中；`request` 又包含 snapshot/send。不能将这些嵌套时长累计成总耗时。

| 分类 | 诊断项 | 含义与边界 |
|---|---|---|
| A 网络等待 | `submitToSnapshotMs - serverCriticalMs` | 输出名 `transportAndSchedulingResidualMs`；包含上下行、压缩/排队、原生回调调度和观测开销，不等于纯网络 RTT |
| B 服务器计算 | `validateMs`、`applyIntentMs`、`coreApplyMs` | 当前单次权威操作的计算；去重请求不会再次有 Core span |
| C snapshot 生成 | `snapshotBuildMs`、`snapshotEncodeMs`、`serializationMs`、`snapshotBytes` | Build 包含该接收方授权模型、战报及 forcedAction 推导；bytes 是 UTF-8 JSON，非 WS/TLS 压缩线速字节 |
| D 客户端重建 | `parseAndEnvelopeMs`、`validationMs`、`reconstructionMs`、`clientApplyMs` | apply 是同步 receive/notify，包括真实页面接入时的同步 UI 工作；不含异步 paint |

`serverCriticalMs` 从同一个服务器时钟的 receive 到操作方 snapshot send，包含排在其前面的另一接收方投影/发送工作。操作方自己的 Build 时长不是两人的构建总成本。

关联规则：连接 + SUBMIT_ACTION `requestId`（即 action id）→ ACK `acceptedRevision` → 非 resync snapshot 的 revision 和紧邻接收方 sequence。Snapshot 自身不添加 action id。等待方没有该动作的 submit/ACK，不以其时钟减操作方时钟。重复请求、缺少阶段、环形缓冲截断时，分析器保留 unknown/null；不补零制造完整链。action id 不包含动作类型或内容。

客户端/服务器均记录 epoch timestamp 和各自 monotonic timestamp。epoch 只用于定位记录，**不直接跨机相减**，也不拆算单向网络延迟。UI Ready 是同步 session 就绪代理，阶段交接时可能 `ready=true, interactive=false`，不代表该玩家有行动权。它不是像素已显示的证明。DOM 交互标志沿用既有观测。

Node v24.19.0 / Windows，两个生产 LobbyClient + NetworkPlayerSession、真实本机 WebSocket、原有权威服务器及 permessage-deflate；无 DOM、无渲染、无模拟 WAN。v2/v3/v3/v2 四轮，每轮 10 次部署，每种格式 20 次。每次均验证两方 revision 一致、等待方无隐藏敌方单位；QUERY_MATCH=0、RESYNC_MATCH=0。

## 四项检查结果

1. **Snapshot 仍可缩小，但不能只看体积判断瓶颈。** v2/v3 每个动作仍发送完整授权 snapshot；v3 表格编码不等于 Delta。地图重复字段已减少，但当前地图值与完整模型仍重复交付。v1 恢复有意保留。MATCH_QUERY 仍返回完整授权模型，未使用 snapshot-v3 的编码入口；非部署阶段需单独量测。
2. **正常部署未发现重复发送。** 一次 SUBMIT_ACTION 对操作方一个 ACK，各玩家各一个独立授权 snapshot。向两位玩家各发送一次不是重复。重放同 requestId 仅返回收据，Core 不重算；sequence gap、断线/恢复和能力协商可合法产生额外 snapshot。诊断可按连接/revision/sequence 区分。
3. **未发现不必要的对手确认或 ACK 定时等待。** ACK 清除 transport pending，但 session 的 submitting 保持到授权 snapshot，是状态正确性的需要。没有等待动画结束。部署按钮已有即时“提交中”提示，因此不应把再加一个 loading 当作实际延迟修复。
4. **可以研究局部更新，当前未实施。** 客户端可先比较授权模型并局部更新 DOM，无需修改协议；适合只显示意图/选中态的反馈。非部署阶段 `ready` 同时受 flight/queued Query 约束，snapshot 后的投影请求可能形成额外往返。其合法选项由服务器生成，不能一概删掉；需要针对真实移动/战斗交互看 `query-build`、MATCH_QUERY 收发及 UI-ready 记录。

## 推荐优化顺序与风险

| 顺序 | 建议 | 预期作用 | 风险与准入条件 |
|---|---|---|---|
| 0 | 用本诊断在受影响 iPad 和目标服务器做一次完整采样 | 先把 A/B/C/D 分开，核对实际格式/压缩协商/版本 | 诊断本身增加解析、事件和报告渲染成本；需要标记 LOD、设备和环境；缺服务器阶段就保持未归因 |
| 1 | 将即时反馈覆盖所有显式 Action；审查主线程反馈何时真正绘制 | 降低“点了没反应”的感知等待 | 复用部署已有反馈；不提前解锁 mutation，不将 ACK 当作已落子；相机和只读查看保持可用 |
| 2 | 仅做 presentation 层的乐观意图标记，例如待确认位置/路径 | 使等待可见、可理解 | 必须标注 pending；只使用已授权/玩家输入信息；拒绝、断线、revision 变化、FOW 消失时清除；不预测战斗、骰子、资源、可见敌军或 Core 结果 |
| 3 | 若 Query 往返或 D 主导，消除实测多余 Query、局部重绘及重复副本处理 | 降低多次往返或客户端工作 | 选项必须对应相同 viewer/revision/draft；不得复用过期合法选项或破坏副本隔离；性能修改另开评审 |
| 4 | 若 C 或数据传输主导，再设计 Snapshot 分级 | 按初始化/恢复、普通权威变更、只读投影区分成本 | 这是后续协议设计：不能把客户端必需的 canAct/forcedAction/pendingDecision/FOW 等推迟成不一致的半状态；当前不落地 |
| 5 | 分级仍不足时再设计每位玩家独立的 Delta | 减少完整地图与模型重复传输 | 风险最高；必须先投影/脱敏再 diff，绑定 viewer+match+baseRevision，原子 apply，删除/失去可见性显式处理，丢包/重连回到完整授权快照；不能发送全 GameState diff |

若 A 主导，先核对实际协商、发送缓冲、服务器关键路径及浏览器调度，停止盲目叠加编码方案。若 B 主导，本任务只报告证据，不改 Core。服务端顺序构建两份视图可能让第二位玩家等待前一份构建，应按角色交换采样确认；不能为抢先响应跳过授权投影。

## 使用方式

这些新增诊断尚未发布到线上。先在受控测试构建/目标服务器接入本改动，核对双方代码版本，再采集。

1. 正常游戏入口加 `?transportDiagnostics=1`；保留当前 snapshot 格式，记录设备、Safari/OS、网络/VPN、缩放、动画与 Unit Models 设置。无需先强制 v3。
2. 打开诊断面板，点击一次 Refresh，确认服务器证据已开启；等待地形 LOD 完成，再执行 10 次常规部署。若测试移动/战斗，单独一组，不混合统计。
3. 操作完成后再 Refresh 一次，立即导出 `eastfront-mp007-diagnostics.json`。服务器最多保留 64 条 send、512 条 stage，断开即清理；客户端最多保留 5 连接、64 动作及每连接 512 个 action timing。Refresh 不应夹在待确认操作中。
4. `node scripts/mp007/analyze.mjs <导出文件.json> <分析输出.json>`。`inputAt=null` 表示没有同步捕获输入，不能推算点击延迟。未完成、拒绝、重复、旧服务器无 stage 或截断样本不能算成快速成功。
5. 若确有必要比较格式，按 MP-006 的同设备 ABBA 方案，分别确认 actual format；不要跨设备/网络混算。诊断无法证明 paint，需要另取 Safari 主线程/画面证据才能判断视觉就绪。

本地复现：`npm ci --ignore-scripts --offline`（需已有缓存），`npm run build`，`npm run server:build`，`node scripts/mp007/measure-local.mjs`。采样只生成元数据证据，不连接生产房间。
