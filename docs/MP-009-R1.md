## 诊断缺陷、修复与反证

原诊断在 pending 意图存在且 `next.matchRevision > pending.baseRevision` 时即发出完成记录，没有等待匹配 ACK；无关较新 snapshot 可能归入本请求。意图被恢复流程清理后，又会漏记实际已经收到精确结果的完成。

新增 `ActionCompletionDiagnostics`，仅在 `transportDiagnostics=1` 时创建。提交时保存 requestId、match/viewer 范围、提交前 revision/sequence；ACK 固定该请求的 acceptedRevision；snapshot 在实际写入授权模型后记录 revision、sequence、`performance.now()`。完成条件是相同范围的精确结果版本、应用序号晚于提交基线，以及匹配请求 ACK。重复 snapshot 保留第一次实际应用时刻，重复或冲突 ACK 不重复产生完成。拒绝取消该请求，dispose 清理记录。

诊断与待确认 UI 生命周期分离：UI 清理后仍可关联已 ACK 的精确恢复 snapshot；它不修改意图状态、正式模型、查询调度、超时或恢复逻辑。示例：snapshot 在 20 ms 应用，ACK 在 90 ms 到达，完成事件在 ACK 回调发布，但 `at=20`、`clientTimestamp=performance.timeOrigin+20`，不是 90。消费者应按 requestId / revision 和记录时间分析，不能把事件派发顺序当时间顺序。

定向测试包括：未有匹配 ACK 的较新 snapshot；snapshot 先到、重复 snapshot、晚到和重复 ACK；ACK 先到；无关结果 revision；UI 清理后的精确恢复；不同授权 viewer。真实权威模型在测试中立即更新，诊断没有成为应用门禁。

同一组 6 项测试在原 `33e7…` 客户端上 **1 通过、5 断言失败**，修订客户端上 **6/6 通过**：[原缺陷复现](../evidence/mp-009-r1/original-correlation-red.txt)、[修复结果](../evidence/mp-009-r1/candidate-correlation.txt)。原版失败不是缺失依赖或构建错误。

限制：只覆盖已提交的部署和普通移动；未收匹配 ACK、仅收到更晚 revision 或该精确版本根本未应用时，不猜测完成。暂存上限为 64 个请求、64 个范围/版本应用记录、128 个完成 ID；超长期丢失 ACK 超出留存窗口可能缺记录，不会用到达时间伪造应用时间。只有数字与请求元数据进入诊断事件，无坐标、单位、token 或 snapshot 内容。

## 恢复计数与触发原因

原始 `evidence/mp-009/` 全部逐字节保留，逐文件 SHA 对照见 [verification.json](../evidence/mp-009-r1/verification.json)。[原记录提取](../evidence/mp-009-r1/original-recovery-audit.json) 保留两套时钟，禁止跨浏览器/服务器的 performance 时钟相减。

| 原浏览器事件 | 浏览器时刻 ms | 可确认信息 |
| --- | ---: | --- |
| 第一次超时提交 | 336735.4 | 请求 `e6e99049…` |
| 第一次 RESYNC_MATCH | 346737.0 | 约 10 秒后，恢复 UI seq 16 / rev 2 |
| 第二次超时提交 | 407374.0 | 请求 `82ef033b…`；ACK seq 21 / acceptedRevision 3 |
| 第二次 RESYNC_MATCH | 417376.9 | 请求 `4f7679f1…` |
| 第二次恢复 UI | 419419.1 | seq 23 / rev 3 |
| 第三次 RESYNC_MATCH | 419456.0 | 请求 `fa35a7c6…`；距上述恢复 UI 约 36.9 ms |
| 再次恢复 UI | 419491.1 | seq 25 / rev 3，后续 Query seq 26 |

原夹具对每个出站消息独立设置计时器，并用 `until-Date.now()` 算延迟，没有显式 FIFO 队列。旧普通 snapshot 与恢复 snapshot 接近同一截止时间时，具有夹具出站顺序风险。**这是从源码和原时间线得出的候选解释，不是原现场乱序已被记录。** 原证据没有被丢弃普通帧 seq 22 的原始接收时刻，也没有第三次调用的触发原因。

新重放使用真实 RoomAuthority、LobbyClient、NetworkPlayerSession 和 snapshot codec，经 JSON 序列化的进程内 WebSocket 适配器传递。虚拟时间保留原 10000 ms 超时、1800 ms ACK 与 12000 ms snapshot 延迟；两个合法普通 MOVE。分别记录 `server-generated`、`fixture-scheduled`、`receive`、`send`、`resync-trigger` 以及客户端诊断；服务帧含 requestId/revision/serverSequence，提交含 expectedRevision，恢复触发含期望序号和原因。RESYNC_MATCH 请求本身没有新增序号字段。

| 同条件客户端 | FIFO：超时 / RESYNC / Query / 提交 | 第二个旧 snapshot 晚到：超时 / RESYNC / Query / 提交 |
| --- | --- | --- |
| 开发基线 `73d2…` | 2 / 2 / 2 / 2 | 2 / 3 / 3 / 2 |
| 原 MP-009 `33e7…` | 2 / 2 / 2 / 2 | 2 / 3 / 3 / 2 |
| R1 | 2 / 2 / 2 / 2 | 2 / 3 / 3 / 2 |

故障注入明确将第二个普通 snapshot 延后 1 ms，不改其序号。三个客户端均在 10000 和 22002 ms 因 `snapshot-deadline` 恢复；乱序场景在 24003 ms 收到旧 seq 7，而当前期望 seq 10，触发 `ordered-frame-check`，第三次恢复随即发生。额外 Query 是再次恢复后既有投影刷新。FIFO 没有额外恢复，所有场景只提交两次动作，最终权威 revision=2、两个合法移动完成。

完整 6 份追踪位于 [recovery](../evidence/mp-009-r1/recovery/)，每个 development / mp009 / candidate 目录均有 `fifo.json` 和 `second-snapshot-after-resync.json`。开发基线与原版的多人客户端模块逐个由对应 Git 源码重新转译，依赖采用已核对无差异的共享代码；未把候选 NetworkPlayerSession 冒充旧版。来源清单可在重跑后的 `node_modules/.cache/mp009-r1/*/provenance.json` 查看。

结论限于这两组同条件对照：额外恢复机制在开发基线已有，R1 无需更改恢复代码。不能为减少次数跳过真实失序检查，也不能凭重放确认原浏览器那一帧的来源。重放不是实际网络、压缩传输或 Safari 调度测试；原浏览器证据和截图保留，本次没有新增真机或浏览器录屏。
