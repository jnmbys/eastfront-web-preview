# EASTFRONT MP-002 — authoritative gameplay synchronization

Baseline: MP-001 `fda6d17b0f08654bce6d36a3944a123a494cdb50`, tree `571f69519f1ff19ce005492cb6b02d04fc5d61f8`.

## Run and host

Node 22+. `npm ci`, then `npm run server` starts the standalone backend. `PORT`, `HOST`, `ALLOWED_ORIGINS`, `RECONNECT_GRACE_MS`, `EMPTY_ROOM_TIMEOUT_MS`, and `ROOM_TIMEOUT_MS` retain MP-001 configuration. For local clients:

```
MULTIPLAYER_SERVER_URL=ws://127.0.0.1:8787/ws npm run build
npm run preview
```

GitHub Pages remains static client hosting; configure an independent HTTPS/WSS server through `MULTIPLAYER_SERVER_URL` at build time or `multiplayer-config.json` at runtime. The shipped production URL is blank. Exact allowed origins are mandatory. No cloud backend was deployed.

`npm run test:mp002` runs retained room tests and gameplay/network tests. `npm test` includes all regressions. `npm run verify:mp002:browser` runs two Playwright contexts; `MP_CHROMIUM_EXECUTABLE` optionally selects an installed Chromium.

## Authority and protocol

Protocol **2** uses exact envelope and nested DTO schemas. MP-001 room/lobby messages and ownership remain. Added:

- `SUBMIT_ACTION {matchId, expectedRevision, action}`; envelope `requestId` identifies the controller's attempt.
- `ACTION_ACCEPTED` / `ACTION_REJECTED`: current ordering plus original accepted revision/action sequence or a safe error code. No raw Core result, action, dice input, state, or Core event is returned.
- `QUERY_MATCH {matchId, expectedRevision, draft}`: bounded presentation selection/path drafts only. Replies contain a server-derived authorized UI projection and, when appropriate, an ordinary forced-transition Action suggestion.
- `RESYNC_MATCH {matchId}`: current authorized snapshot; no viewer selection.
- `PLAYER_VIEW_SNAPSHOT`: `format: snapshot-v1`, `matchRevision`, `serverSequence`, authorized PlayerView, UI options, status, canAct, and filtered presentation events. The format discriminator reserves future patches without implementing fragile diffs now.

All mutations enter the synchronous RoomAuthority path. Match and connection membership precede revision/ownership/Core checks. Pending-decision controller supersedes active-side controller. The frozen RulesEngine validates phase and detailed legality. Core action/controller/new battle identities are server-assigned. Administrative transfer/commitment capabilities are excluded from two-seat Scenario rooms. Unknown actions, Observer, state, seed, result, or extra fields are rejected before Core.

Accepted actions increment revision and actionSequence once. Controller/match receipts survive reconnect; identical request IDs replay an ACK reference, including when the caller's expected revision has become stale. Changed payloads with the same ID are rejected. Receipts are retained for the entire match, capped at 4096 attempts per controller; exhaustion rejects further attempts instead of evicting receipts and risking re-execution. Order-insensitive object serialization preserves semantic retries; array order remains meaningful for paths/losses/retreats. Room/token entropy never touches gameplay RNG.

Each recipient has its own monotonically increasing `serverSequence` for gameplay replies and updates. Lobby revisions use the existing room stream. The client requires contiguous sequence and a valid match revision; gaps/reordering trigger resync. A resync snapshot establishes a fresh sequence and clears drafts and animation work. ACKs never apply movement; a missing post-ACK snapshot times out into resync.

## Privacy and queries

The server creates the official production Scenario through the existing fresh-seed path. `dispatchGameAction` reuses the frozen engine and existing per-viewer `rememberPlayerView` logic. The server retains separate German/Soviet knowledge. For each action it captures previous authorized views, applies Core, then derives new views and filters existing presentation events independently per viewer.

The browser never creates a GameState for a network match. `NetworkPlayerSession` owns received DTOs only. Hidden deployments reveal no enemy IDs/types/positions/animation. Hidden travel has no route event; artillery cues require a legally known supporter. Network event identifiers contain presentation revision/index, not hidden action details. Query drafts cannot choose another viewer or upload knowledge. The trusted projector restricts selection to visible/owned units, private pending contexts to their owner, battle history to disclosed battles, and diagnostics to codes without units/hex/details. Queries and forced-transition suggestions do not mutate Core or its RNG.

Legal move, retreat, reinforcement and combat options come from the same existing Core queries/projector. No alternative rules engine or movement legality implementation was added. UX2 forced no-choice transitions are suggestions sent only to the connected decision owner and submitted as ordinary validated Actions. No decision is automatically submitted by the server while a controller is disconnected. Partial retreat routes remain drafts until a server query confirms the entire ordered action.

## Shared client and reconnect

The existing map, Counter/Model, animation runtime, Combat UX2.1 panels, camera and continuous Fog renderer consume a Local/Network session adapter. Local/hotseat play remains independent of the backend. Network selection/path highlights are local presentation; canonical positions, losses, phases, victory and fog change only on authorized snapshots. Pending actions disable commands. Status messages are Chinese by default and fully bilingual.

Any disconnected match member freezes the network match as `WAITING_FOR_RECONNECT`. Within the existing 60-second grace, the token reclaims the controller and gets current revision, authorized view, and its pending decision context, with no old animation replay. Expiry/leave/idle shutdown ends the network session as `ABORTED`, without modifying Core victory. Only Core's formal GAME_OVER/victory yields `FINISHED`. Storage is process memory; restart recovery, persistence, surrender/timeout wins, spectator roles and AI takeover are out of scope.

## Validation and performance evidence

`evidence/mp-002/network-e2e.json` records a real two-WebSocket production Scenario: 224 accepted actions, both hidden deployments, move, multi-attacker combat, reconnect, mandatory reinforcements and all phases through Turn 16 official victory. Every accepted action compares server GameState, knowledge and RNG to the same local sequence. A separate frozen-Core combat fixture covers retreat, advance, breakthrough, Schwerpunkt and reconnect during a defender decision. Fixtures inject known seeds only into the test server factory; clients cannot select a seed or upload a fixture.

Other tests cover loss ownership, hidden artillery/travel, CONTACT/Last Known, stale/duplicate/malicious messages, invalid tokens, grace expiry, sequence gaps, query coalescing, and observer denial. Existing local/FOW/Combat/Performance tests remain gates. Frozen checksum exceptions are limited to the main integration boundary, animation subscription adapter, package scripts, and test harness imports; see `frozen-adapter-exceptions.json`. Core, rules, FOW semantics, spotting, fog pixels, camera math, VS2 and model artwork remain byte-identical.

Full snapshots are deliberately conservative. Local E2E timings include JSON transport, server application/projection, and test-side equivalence/privacy assertions; they are not Internet latency measurements. Selection queries retain the received PlayerView object; equivalent observation masks do not rebuild Fog. Ordinary updates use DynamicMapRenderer, preserve the current VS2 surface and camera, and never client-derive PlayerView. Terrain is built lazily once after entering a match. Room/connection chatter updates status, not map rendering.

Known limits: two-controller, single-process, memory-only server; full snapshots and query round trips rather than deltas; no offline action queue; no automatic takeover; no persistent reload after server restart. Huawei validation uses a Chromium Android tablet profile, not physical Huawei hardware.
