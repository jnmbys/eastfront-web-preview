# MP-016：权威应用后的查询调度等待

日期：2026-10-03。分支：`mp-016-query-wait`。开发基线完整 SHA：`4db081bcfcd89c584fe7f53015b2a6ade63d87bf`。本轮仅本地构建、定向夹具和回环 WebSocket 验证，无公网入口、无合并、无部署。

## 结论

普通移动完成后的这一次 QUERY_MATCH **仍然必要**：snapshot 是默认草稿的授权模型，没有当前选中单位在新 revision 下的路线合法选项。本轮不删除查询，不沿用旧目标，也不放宽 ready / interactive。

已修复一段可证明不必要的调度等待：原来 `requestProjection` 把发送放入零延时定时器，必须等 snapshot 触发的同步界面重建完成才发出。现在仅在普通移动阶段、无待处理强制决策的 snapshot 刷新窗口，现有渲染入口请求投影时立即发送已经确定的同一个查询，使等待回复与本地界面重建重叠。没有新增预取，没有多发查询；其他选择仍保留同一轮合并和单在途请求限制。

固定夹具为 ACK 200 ms、snapshot 400 ms、查询回复等待 700 ms、同步渲染 120 ms：恢复操作从 1220 → 1100 ms，减少的恰为模拟的 120 ms 渲染阻塞。查询仍为一次，查询等待仍为 700 ms，权威完成与允许选择均仍是 400 ms。渲染成本为零时没有收益；snapshot 先到、ACK 晚到时没有虚构收益。**这些是人工夹具结果，不能宣称华为或网络延迟降低。**

## 查询链与真实数据依赖

1. `server/authority.ts` 的 snapshot 调用 `queryModel(match, controllerId)`，没有传入客户端草稿；它包含当前授权视图和默认投影。
2. `NetworkPlayerSession.receive` 立即应用 snapshot，更新 revision/sequence，清除旧动作草稿、保留仍可见的选中单位，并使 `modelKey` 失效。
3. `main.ts` 的 `refreshDynamicView` 在更新地图和面板前调用 `requestProjection(presentation)`。key 含当前 matchRevision 和完整 QueryDraft。
4. `QUERY_MATCH` 发出 `expectedRevision` 与草稿。原服务器校验身份、拥有权及版本；旧版本请求返回恢复 snapshot，否则从 Core/授权视图计算当前投影及 forcedAction。
5. 客户端只接受 requestId、当前 revision、当前 draft key 均匹配的回复。旧查询仍消费合法序号，但不覆盖当前选择；真实失序仍恢复。
6. 查询槽释放、模型生效后，原 `interactive` 门禁恢复，后续动作仍经服务器及 Core 校验。

| 查询补充的数据 | 依赖操作 | 可否仅由当前 snapshot 独立完成 |
| --- | --- | --- |
| 当前选中单位和路线的 movement / moveOptions、消耗 MP、合法性问题 | 开始/扩展路线、目标可用性与确认移动界面 | 否；选中单位的新版本选项须查询 |
| railRepair 的工程兵/边草稿与校验，recovery / entrench 的选中单位校验 | 修铁路、恢复、构筑 | 否；本轮不调整这些阶段 |
| reinforcement 选择投影，combat 草稿、反应/损失/撤退/突破等选项、forcedAction | 对应合法目标及强制决定 | 依赖当前授权查询；本轮保留原调度 |
| 当前可见棋子、正式位置、资源、viewer 和 phase | 展示正式结果、单位资料 | 是；snapshot 已授权，不等查询改变正式状态 |
| 本地选中单位、撤销/取消草稿、地图拖动缩放 | 纯本地交互 | 原 MP-003 已允许独立选择和视口操作，本轮不改变其定义 |

不能将 MATCH_QUERY 仅视为一次无内容确认。客户端没有足够信息安全地补算隐藏敌军或阻挡；本轮不推演这些信息。

## 最小实现范围

- `src/multiplayer/networkSession.ts`：仅在 revision 变化或恢复 snapshot、普通移动阶段且没有 pendingDecision/forcedAction 时，为同步 `onChange` 回调开启发送窗口；`try/finally` 关闭窗口。渲染函数主动请求投影时，沿用 queued → flight → send；未请求则不产生查询。
- 即时发送前仍检查单在途请求、submitting、syncing、queued、client.canMutate、needsProjection。若 snapshot 先到但 ACK 未释放提交/传输槽，继续等待；不抢占旧查询。已有定时器被同一最新请求替代时先取消，不会双发。
- 普通选择、快速 A→B→A、过期查询后的重排、拒绝和强制决策保持原合并调度。新请求使用新 revision，旧合法选项保持隐藏。
- `src/multiplayer/diagnosticTiming.ts`：增加仅启用诊断时发送的本地 `interaction-gates` 事件，不是网络协议字段。仅含时间、请求关联、revision/sequence 和布尔状态；不含单位、目标、路径、游戏载荷或凭据。

### 四类时点的固定口径

| 时点 | 观测来源 | 含义 |
| --- | --- | --- |
| 动作完成 | 原 `snapshot-applied` | 匹配 requestId ACK + 实际应用 acceptedRevision；晚 ACK 不改写实际应用时刻 |
| 允许选择 | `canSelect` | 原本地选择门禁；不是下一动作可提交 |
| 合法选项就绪 | `legalOptionsReady` | 当前 revision + draft 对应授权投影可用；不需查询的阶段按原 snapshot 能力处理 |
| 允许提交 | `canSubmit`，值严格等于原 `interactive` | 原整体提交门禁；不表示任意动作已经通过规则校验，具体按钮/路线合法性和最终服务器判断仍保留 |

新诊断在投影请求/回复应用、提交、连接状态和恢复边界记录这些状态。原 `ui` 与 `snapshot-applied` 语义不变。夹具在修复前从相同既有门禁/key读取状态，修复后增加本地事件；均使用同一个客户端单调时钟。未观测值为 null，不作为零。四种时点不会被合并成一个更早的“可操作”指标；没有以 rAF 代替实际绘制时间。

## 现场依据与本地对照必须分开

MP-015 华为对照单次：原采样器权威应用 859.6 ms、恢复操作 1747.8 ms。诊断同一 iframe 时钟内：应用→查询发出 118.5 ms，查询发出→收到 715.6 ms，收到→恢复操作约 54.0 ms，总计 888.1 ms。应用至消息处理结束为 84.5 ms，其后至发出为 34.0 ms。这支持审查调度接缝，但不能证明整段 118.5 ms 都能在真机消除，也不能把 715.6 ms 直接称为纯网络耗时。
