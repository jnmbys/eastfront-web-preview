# MP-020：移动后必要查询分段诊断

结论：华为记录中最大未解释区间仍是 QUERY_MATCH 发送到客户端消息回调的 **707.2–956.1ms**。本轮同场景的隔离实例没有复现这段长等待；没有证据证明应删除必要查询、再改调度或增加缓存，因此只补诊断，**未实施性能修复，也没有可宣称的提速量**。不能把旧记录减去本地服务端耗时，得出华为网络 RTT。

## 实际路径与关联

客户端保持 `snapshot 应用 → restoreDrafts → onChange → requestProjection → flush → LobbyClient.send → QUERY_MATCH`。普通移动继续在同步渲染之前发送；一个在途请求加一个最新未发送草稿。query key 同时绑定草稿和 revision；当前 requestId、revision、草稿不匹配的结果不应用。查询回复通过这些检查后才应用合法选项并解除原门禁。

服务端：`WS message callback → data.toString/parseClientMessage/重复请求检查 → handle 的成员及版本校验 → queryModel → forcedAction → battleSummaries → order/emit → JSON.stringify → ws.send → write callback`。这条路径同步执行，没有应用层查询排队器；消息进入 JS 回调之前的内核、解压和事件循环排队不可观测，保留缺失。`queuedAt=null` 不是测得排队为零。

还检查了现场验收接缝：MP-017 固定夹具在 authority 输出侧有 FIFO，`real` 条件的 ACK/snapshot 人工延迟均为零，正常直接泵出；另外两种人工模式保留延迟。4180 网关与本人边界在升级后按字节流双向 pipe，没有新增逐条 query 计算。当前分段主运行直接连隔离游戏实例，**没有经过这两个代理、TLS 或 cloudflared**，也没有并发压力；不能据本地几毫秒排除现场代理背压、发送队列或事件循环繁忙。

查询提供当前选中单位/草稿的新版本合法移动及其他交互选项。snapshot 的默认草稿不能替代它。`MATCH_QUERY` 仍包含完整授权模型，snapshot-v3 编码只作用于 snapshot；本轮没有改变任何回复字段。

`queryModel` 中授权视图过滤与投影分别调用既有构建路径；本轮整段仅数毫秒，没有证明其中哪一步可在保持过滤语义下安全删去。`forcedAction` 在普通移动无待决策时立即返回，未观察到第二次完整查询计算。没有以跨请求/跨玩家缓存交换权限风险。

## 诊断改动

仅修改 `server/authority.ts`、`server/runtime.ts`、`server/latencyDiagnostics.ts`：

- 新增进程内可选 `LatencySink`，不新增访问端点、认证方式或线上消息字段。默认未订阅时不开计时；观察器异常隔离。原传输诊断仍可单独启用。
- requestId 关联 WS 回调入口到同步处理分发、查询模型、强制决策、摘要、序列化、交给发送接口及写回调；记录 revision/sequence、字节数和本地缓冲量。`query-build` 包含模型/强制决策/摘要，不能重复相加。
- 客户端复用 MP-016 已有发送、回调、解析、`query-applied` 和交互门禁事件，保存同一客户端单调时钟下的时点；没有重写状态关联、延迟 snapshot 或改变允许提交定义。
- 本地夹具在独立服务端进程运行真实 authority/Core/WS 和真实 LobbyClient/NetworkPlayerSession。使用 MP-017 完全相同场景准备函数、种子 17、v3 snapshot、既有压缩设置。测试脚本断言场景函数与原文件一致。
- 保存 metadata 和授权结果的 SHA256，不保存 payload、单位/目标/路径、口令、cookie 或 token。WS 帧计数复用既有帧解析器，只导出长度/压缩标志，不保存帧内容。Node 适配器为关联帧额外解析一次 JSON，两组采用同一包装；本地绝对耗时包含其成本。

服务端时钟和客户端时钟独立。只计算各自持续时间；`unknownResidualMs = 客户端 send→callback 持续时间 − 服务端 receive→handoff 持续时间`，不是不同机器时间戳相减。该剩余包含传输、WS 压缩/发送队列、回调前排队和客户端调度等，**不是纯网络 RTT**。写回调也不是对方收到确认。缺失项为 null，不按零处理。

### 原华为现场（未重测）

原四次恢复查询收发分别为 **864.6、897.6、707.2、956.1ms**；收到后至允许提交为 **12.7、18.5、23.7、11.1ms**。候选两次 snapshot 应用到发送仅 **3.8、1.8ms**，查询等待与同步渲染已重叠。因此，已记录的主要等待在消息回调之前，尚不能分解为服务器、隧道、网络或设备排队。

第二组 A 的额外查询在首次允许提交之后约 3.57 秒才发送，不是此次恢复的前置条件。没有草稿变化证据，不能称它为重复查询缺陷。原用途标签仍为暖机/用途未确认探索，正常性能样本数不改。

### 本地真实查询（5 次基线、5 次带诊断）

| 指标 | 带诊断范围（ms） |
|---|---:|
| 客户端发送 → 回调 | 5.026–7.130 |
| 服务端入口 → 分发 | 0.041–0.106 |
| 查询模型计算 | 2.866–3.527 |
| 强制决策 | 0.002–0.003 |
| 摘要 | 0.002–0.016 |
| 序列化 | 0.549–0.686 |
| 服务端入口 → 交给发送接口（总段） | 3.488–4.221 |

每次移动 **1 action、1 必要 query、0 resync**；拒绝重复点击，权威位置未提前变化，操作确实恢复。原基线与带诊断、人工等待各组的授权结果摘要一致；另一玩家得到自己的只读授权结果。

回复序列化 **171150 字节**；压缩后 WebSocket 帧含帧头约 **15655–15660 字节**，不含 TCP/IP/TLS 开销。5 次 `bufferedBefore=0`，无写错误；不意味着在远程链路或并发压力下始终无积压。

原基线收发 **5.143–6.883ms**，中位数 **5.452ms**；带诊断 **5.026–7.130ms**，中位数 **5.739ms**。这是诊断一致性对照，有采样顺序、JIT、系统负载等波动；没有性能修复，不能把范围差或 **+0.287ms** 中位数差视为稳定变化或精确探针开销。可归因减少量：**未证明**。

### 人工延迟，不能替代真机

- 2 次回调人工等待 700ms：客户端收发 **709.277–712.854ms**，服务端总段 **3.838–4.946ms**。这是夹具施加的等待，不能倒推华为根因。
- 2 次 snapshot 同步工作 120ms：客户端收发 **124.927–127.059ms**，服务端总段 **3.686–4.478ms**。MP-016 仍提前发送；客户端忙时即使服务器已写出，回调也会迟到。该例直接说明剩余不能命名为纯网络耗时。
- 所有组均只发 1 次恢复所需查询，授权结果和门禁保持一致。没有浏览器 DOM、绘制或真机性能结论。

首轮本地探针开发时另一玩家的测试草稿错误使用空对象，协议正确拒绝，夹具等待超时；随后修正为 `queryDraft(createPresentationState())`。不是现场缺陷或成功样本。`initial/fixture-failure.json` 保留这一事实。前置成功探索位于 `local-diagnostics/`、`wire-diagnostics/`，不与正式主运行混算。
