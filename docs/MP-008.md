# MP-008｜多人交互即时反馈实验研究

日期：2026-10-02。任务对象：网络 Worker。状态：研究报告完成；未实现候选反馈功能，未部署，未改协议。

## 决策

**值得实现第一阶段的小规模实验：部署和移动的即时请求提示，加上明确标注“待确认”的目标/路径标记。** 预计收益是让玩家立即知道输入已被处理，减少盲目重复点击；不会缩短网络确认时间，也不会提高连续操作吞吐。

正式棋子、位置、资源、可行动性及 FOW 仍只由服务器授权 snapshot 决定。收到 `ACTION_ACCEPTED` 时显示“已接受，正在同步”；收到并应用有效授权 snapshot 后才正式替换。不能把“服务器确认”简化成 ACK 到达即移动正式棋子。

建议顺序：**统一即时提示 → 部署目标标记 → 移动待确认路径 → 真机评估 → 有条件研究局部 Snapshot/分级同步 → 最后评估 Delta**。第一阶段可不改协议；第二、三阶段本次只研究，若以后改变传输内容，需要另行协议设计及兼容评审。

## 1. 当前延迟链与已知边界

```text
Input
 → Client Send
 → Server Receive
 → 校验 / 去重 / Core Apply
 → ACTION_ACCEPTED
 → Snapshot Build / Encode / Serialize
 → Network Send
 → Client Receive / Parse / Validate / Rebuild
 → 应用授权状态 / UI 更新
 → UI Ready
```

移动在提交之前还可能有：选择单位/编辑路径 → QUERY_MATCH → 授权投影；snapshot 应用后也可能为新 revision 请求投影，因此“棋子位置已更新”和“下一次操作可用”应分开表达。

沿用 [MP-007](MP-007.md) 的结论：主要可观察等待位于 snapshot 到达客户端之前，但 iPad/Safari 的具体根因仍未确认。历史公开 Cloud Chrome v2 部署样本中，发送→snapshot 中位数约 535 ms，发送→控件就绪代理约 571 ms；这是历史数据，不是本次真机测试。MP-007 本机 v2/v3 的 session 就绪均约 23 ms，也不能用来预测 iPad 的收益。

本实验增加一条短的展示路径：

```text
Input → 现有提交门禁 → 设置本地请求提示/待确认标记 → 浏览器呈现
                └→ 原有网络与权威状态链照常执行
```

应直接发送原有请求，不等待动画、定时器或下一帧。DOM 文案写入不等于像素已经呈现；若随后同步重建阻塞主线程，即时反馈仍可能晚显示。这是实验需要测量的重点。

## 3. 第一阶段：可实现的交互方案

### 部署

点击确认并通过现有提交门禁后，保留按钮“部署请求处理中”，目标格出现一个带“待确认”标签的虚线边框。复用己方已授权 roster 的类型名称；首版使用目标框即可，无需复制真实棋子模型。

不增加正式 counter，不把 roster 改成已部署，不提前选择下一个单位，不更新堆叠、资源、行动权或视野。ACK 到达后只把提示改成“已接受，正在同步”。有效 snapshot 应用时，在同一轮 UI 更新中移除标记并显示服务器正式棋子，避免出现两枚棋子或短暂叠加。

### 移动

点击“确认移动”并通过门禁后，保存本次提交的路径副本，显示虚线待确认路径、目标框和“移动请求处理中”。原位置的正式棋子保留原状。预览只表示玩家提交的意图；不要显示“已移动”、新剩余移动力或下一段可达范围。

ACK 后继续保留待确认样式；授权 snapshot 到达后，正式位置与服务器一致，撤下标记。若已有授权移动动画，交给原动画链处理，不提前播放一次再重放。snapshot 已应用但新 Query 未完成时显示“更新可用操作”，不能继续把整段时间称作“正在移动”。

首版不建议让实体棋子提前走到目标格：即使仅改渲染 transform，也可能被误认为已经完成，并与命中区、堆叠、动画、镜头跟随及 FOW 混用。

### 展示状态机

| 状态 / 触发 | 显示 | 权威状态与操作门禁 |
|---|---|---|
| 编辑草稿 | 现有部署选择/移动预览 | 沿用现有合法选项与 Query 门禁 |
| 本地检查不通过、`send` 返回 null 或抛错 | 未发送；显示当前不可操作/连接状态 | 不创建长期 pending；不自动排队发送 |
| 请求成功交给现有 transport | 请求处理中 + 待确认标记 | 保留正式状态，单个 mutation 在途 |
| 匹配本请求的 ACK | 已接受，正在同步 | 不落子、不移动、不解锁下一次 Action |
| 已按现有顺序校验应用匹配的授权 snapshot | 正式结果替换 pending 标记 | 可操作性仍由 session、canAct、Query 状态决定 |
| 匹配本请求的拒绝 | 请求未执行；清除 pending 标记 | 不需要回滚 Core；沿用拒绝后的草稿处理 |
| 超时、断线、sequence gap、STALE_REVISION | 状态待核实，正在同步；撤下预测标记 | 不把超时说成失败，不自动补发新 requestId 的动作 |
| 恢复 snapshot / 重连完成 | 展示服务器当前状态 | 不复活旧标记；缺可靠收据时只说“已同步”，不宣称旧动作成功或失败 |
| 离房、换 match/viewer、session dispose | 立即清理所有 pending 展示 | 不跨房间、跨视角保留 |

现有 request timeout 为 10 秒（`src/multiplayer/config.ts:1`），不是正常操作的固定等待。本实验无需改它；可在约 1 秒时仅改变提示为“仍在等待服务器”，不新建提前重试逻辑。该阈值属于待验证的 UX 设定。

### 最小本地结构与接入点

建议新增 session 所有的 `PendingActionPresentation`，仅在内存保存：`requestId`、`matchId`、viewer/session 标识、`baseRevision`、动作种类、提交时目标/路径副本、开始时间、展示阶段以及收到 ACK 后的 `acceptedRevision`。不存 GameState 或对手信息，也不持久化到 storage。

- 在 `NetworkPlayerSession.submit` 的成功发送路径绑定现有 requestId；当前方法返回 void，可增设本地返回结果或展示通知，不改变网络消息。`LobbyClient.send` 会同步 notify，设计时需处理发送前后的展示初始化顺序，避免失败仍显示在途。
- 只处理属于这个 pending request 的 ACK/拒绝。snapshot 先经过现有 match、viewer、revision、sequence 校验并实际采用，再依据已接受 revision 收敛展示；不能“收到任意新 snapshot 就播放成功”。恢复时即使目标位置相同，也不凭位置猜测动作身份。
- 独立 pending overlay 使用无命中目标的 SVG 元素，`pointer-events:none`，不注册 `data-unit-id`，不送入 counter、presence、动画事件或 FOW 输入。与地图相同坐标系，明确处理动态层重挂和 camera transform。
- 只更新文字、按钮状态及少量 overlay 节点；不重新构造地图、terrain、授权 DTO，也不为反馈增加 Query。文案可用现有 `role=status` 承载，避免反复播报；用文字/虚线区分状态，不只依赖颜色。
- 部署 pending 和移动 pending 都保持单个动作在途；不提供“撤销已发送请求”。已有取消只作用于未发送草稿。保持相机、缩放和允许的只读查看，不另加全屏阻塞层。

## 4. 同步与 FOW 风险

| 风险 | 典型错误 | 必须满足的约束 |
|---|---|---|
| ACK / snapshot 间隔 | ACK 后把棋子正式移到新位置，下一次动作基于旧 revision | ACK 只推进展示阶段，正式结果必须等 snapshot |
| 双击 / 重绘重复绑定 | 产生多个 requestId 或重复 overlay | 复用现有提交门禁与监听绑定；同一请求只一个标记 |
| 拒绝 / 网络丢失 | 假成功、无限 pending、自动重复执行 | 拒绝清展示；断线/超时进入不确定状态并沿用恢复；不自动重新执行 |
| 旧消息 / viewer 变化 | 旧房间或旧视角出现幽灵棋子 | 以 session、match、viewer、requestId 绑定，失效即清理 |
| 隐藏敌军 / ZOC / 堆叠 | 用本地完整规则预测路径结果，从而暴露隐藏阻挡 | 仅画玩家已提交的路径，不额外判断“肯定能到”，不细化服务器原有拒绝原因 |
| 提前扩展视野 | 以目标格为新单位位置计算 fog/contacts/lastKnown | FOW 只读当前授权 view；pending 不进入任何知识或可见性计算 |
| 对手看到计划 | 将己方部署目标/路径放入共享状态或广播 | 标记只存在操作者本地，不加入消息、分享/导出状态或日志载荷 |
| 视觉与语义错位 | 目标格有可点选正式棋子，但服务器还在原位 | 使用目标框/虚线路径；正式 counter、hit target 和资源不变 |

第一阶段的 FOW 风险可控制在低水平，前提是“预测”严格限定为**意图展示**。如果改成提前运行规则或移动正式渲染对象，风险与测试成本都会明显上升。本地能读取的内容也必须限定为当前授权信息，不能通过新增数据接口获取隐藏状态。

## 6. 实验设计与准入条件（尚未执行）

当前组 A 保留原界面；候选组 B 启用请求提示与目标/路径标记。只改变展示，使用相同服务器、snapshot 格式、网络、设备、视口、模型和动画设置。部署与移动分别统计；用对应场景/同等合法动作交替 ABBA 采样，先每组至少 10 次。样本量仅适合探索，不能宣称稳定提升百分比。

区分三个指标：

1. **首次可见反馈**：点击→文字/标记实际出现。研发阶段可记录 DOM 更新和下一帧代理；真正结论需真机录像或浏览器 trace，rAF 回调也不是 paint 已完成的证明。
2. **权威完成**：Send→匹配 snapshot 应用。预期不因即时反馈缩短，且不应明显回退。
3. **再次可操作**：Input→session interactive，分开报告移动后必要 Query 的时间；同时记录重复点击、误认为动作完成、残留标记和错误恢复。

建议候选工程目标：前台空闲时争取下一帧呈现；真机首次可见反馈 p95 目标 ≤100 ms（待测目标，不是现有成绩）。若原部署提示已经同样及时，则要求候选在定位反馈/误点方面有可观察价值，否则保留更简单的文字方案。若增加主线程阻塞或权威完成时间出现可复现回退，优先简化/移除 overlay，不修改 Core 追求通过。

未来实验必须覆盖：正常成功、ACK 延迟、snapshot 延迟/丢失、服务器拒绝、stale revision、重复点击、重复 ACK、发送失败、断线/重连、恢复快照、phase/match/viewer 变化，以及 overlay 重挂/缩放/面板开合。测试网络延迟只用于故障注入，不作真机性能证据。

通过门槛：每个显式操作保持单次提交；ACK 期间正式位置/资源/FOW 不变；候选与基线最终授权状态相同；不增加反馈专用 Query；失败/恢复后无残留；对手数据中无路径或计划；移除展示开关后行为恢复原样。真机体验改善未经采样前只记“待验证”。

## 7. 第二阶段：局部 Snapshot 与分级同步研究

需要区分客户端局部绘制和网络局部 snapshot：前者不改协议，部署已有；后者在当前 `MatchSnapshot`/codec 要求完整视图的契约下，不能直接少发几个字段。

| 方向 | 实现成本粗估 | 同步与 FOW 风险 | 启动条件 |
|---|---:|---|---|
| 客户端只重绘变化的授权节点 | 2–4 日专项评估/试验 | 中；删除、旧节点、动画/命中层需一致 | MP-007 的 D 或反馈前主线程工作占比显著；部署已有优化，勿重复建设 |
| 局部 snapshot / 按功能分组的授权投影 | 约 1–2 工程周 | 高；跨字段依赖、旧 revision 混用、隐藏实体删除 | C/传输体积有明确成本且可证明完整重建等价；需未来协议评审 |
| 初始/恢复完整同步 + 普通操作关键数据 + 可延后历史展示 | 约 1–2 工程周，可与上项重叠 | 高；部分到达时不能开放基于不一致状态的操作 | 能清楚定义哪些字段允许延后，且晚到数据不改变当前合法操作 |

“关键数据”至少需要一致的视角/顺序、权威状态、位置、阶段、资源、行动权、pendingDecision、可见性及必须的删除语义；实际闭包必须按代码依赖审计，不能先硬编码成“只发移动单位”。这些字段未收齐且未经校验，不得提高 revision 或解锁 Action。

战报/历史等只读内容也可能包含授权约束；延后不代表可跨 viewer 共享缓存。初始、重连、失序和格式回退应保持完整授权恢复。缓存公共地图几何与动态控制/可见性数据必须分开，不能把当前被重复发送的字段一概视为静态。

结论：**值得保留设计研究，当前不值得直接改协议实施。** 先拿到目标环境分段证据及第一阶段体验结果，再决定是优化 D、Query 往返，还是网络负载。

## 8. 第三阶段：Delta 同步可行性

技术上可行，但成本最高，且不保证降低当前主要等待。若固定往返/浏览器调度占主导，减少字节可能改善很小；MP-006 已证明不能将体积改善等同于延迟改善。

未来设计必须满足：

- 每个玩家先生成授权投影，再对该玩家已知的基线求差；严禁对完整 GameState 求差后发给客户端，也不跨视角复用。
- 基线绑定 match、viewer、协议/格式和 baseRevision；目标 revision 明确。重复、乱序、缺片、错基线一律不能部分应用。
- 客户端先重建、验证，再原子替换。snapshot 的删除、FOW 撤回、contacts/lastKnown、数组顺序、null/缺失语义和独立副本隔离必须等价。
- 缺失基线、重连、窗口淘汰或校验失败时走有界完整恢复；不能因差量小而无界保存历史，也不能仅凭 `ws.send` 完成认定客户端已安装基线。
- 需定义基线确认/恢复机制并兼容旧客户端，属于未来协议工作。本次不选择具体新消息或字段。

粗估：离线差量体积/重建等价性验证 3–5 日；稳健实现、回退兼容和双端故障测试约 2–4 工程周，再加真机验证。同步风险高，FOW 风险高，维护成本持续存在。这些时间不与第二阶段简单相加，二者有重叠。

判断：**可行，暂不建议实现生产 Delta。** 只有量测表明完整 snapshot 的传输/构建成本值得承担复杂度，且跨阶段/FOW 等价性试验通过，才进入实现。
