# MP-011-R1：公网匿名 WS 500 诊断与本人入口修订

基线 `3e8d78a67e039ac10ea2eb2943d70fc4138ec9df`，分支 `mp-011-r1`，主机 `LAPTOP-G2NEE96G`。执行日 2026-10-02，证据时间为 UTC。沿用已批准的本人临时 HTTPS 方案，没有再次索取发布权限。最终运行状态与完整交付 SHA 见交付消息和本报告后续验收记录。

## 已确认的现象与推断边界

带诊断、保持原拒绝响应的版本中，六条 WS 路径各重复三次：本地 18/18 为 403；公网 10/18 为 403、8/18 为 500。八个 500 均通过独立 requestId 对应到边界的 received、unauthenticated 拒绝决定、403 response-finish 和无错误 connection-close。没有把缺失日志当作未到达证据。本地 finish 只证明写入本地 socket 完成，不证明代理或公网客户端已接收完整响应。

单变量实验只在原空 403 响应增加 `Content-Length: 0`，保留原 `Connection: close`、socket.end、Host/Origin/会话判断。cloudflared 版本仍为 2026.9.3，两个阶段都固定 QUIC，目标始终是 127.0.0.1:4181。首轮及同一修订地址的复查共 36/36 公网 WS 返回 403；本地也 36/36 为 403。两轮受保护 HTTP 各六项均为 303 登录页，登录页为 200。

这支持明确空响应长度能消除本次观察到的转发异常，但**未证明 Cloudflare 内部的完整根因**。没有边缘内部追踪或同一隧道上的 ABA 反转实验；原失败轮按要求关闭全部进程后，修订轮获得了新临时地址，域名/连接批次仍是混杂因素。没有反复换域名筛选成功结果；修订地址后续保持不变。未将 500 算通过，也未切换 HTTP/2 来叠加变量。[RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3) 支持优先显式标明消息长度，但标准本身不是这次公网 500 的根因证据。

另外发现独立登录问题：本人提交登录后返回 403，补齐原因后明确是 `login-origin`，没有进入口令比较。原登录页的 `Referrer-Policy: no-referrer` 与普通 HTML 表单导航 POST 的严格 Origin 校验冲突；[Fetch 的 Origin 生成算法](https://fetch.spec.whatwg.org/#append-a-request-origin-header) 规定这一情形将 Origin 设为 null。修订只让登录表单 GET 返回 `Referrer-Policy: same-origin`；其余响应仍使用原策略，Origin 缺失、null、外站均不能登录，未允许匿名 WS。原日志没有记录实际 Origin 值，因此具体失败请求的值不能从现有日志回溯为已实测 null；这里是拒绝原因、原响应头与标准算法支持的解释，仍需修订后本人浏览器成功来确认恢复。

探针每条请求仅保存 UTC 时间、路径、请求关联 ID、配对 ID、本地/公网路线、状态、CF-Ray、耗时和退出码；同一配对使用同一路径、合法 16 字节 key、Host/Origin。各请求使用不同 requestId，以免把本地请求误关联为公网请求。边界只记安全的路径白名单、请求 ID、CF-Ray、时间、方法分类、接收、拒绝原因、响应完成与错误代码。未知路径和查询串被归为 `<other>`，不写入任意头、口令、cookie、token 或游戏载荷。

探针 stage 不可覆盖已有输出。停止脚本按 PID、创建时间与命令核对自己启动的进程，顺序为隧道→边界→lab，并检查本地端口及公网状态。临时登录诊断只停止边界以保留同一域名时，先验证原地址 502；不得把隧道目标改为无认证的 4180。最终结束必须停止三个进程。口令只由本人本机输入，未保存，边界重启会清空会话。
