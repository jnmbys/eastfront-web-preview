提交回执和账本刷新现在分开确认。收到COMMITTED后，即使账本连续读取失败，页面明确显示“后端已确认提交；账本尚未刷新”，保留请求ID，锁定照管、推进、恢复。只重读账本，不再POST。拒绝回执同样保留“已确认拒绝”及锁定，直到读到可用账本；不会把拒绝显示成成功。

| 前端状态 | 可执行的恢复操作 | 业务按钮 |
| --- | --- | --- |
| 提交结果未知 | 原ID查询回执；人工重试仍为首次原内容 | 锁定 |
| 已确认提交或拒绝，账本未刷新 | 只GET账本；不再POST或重新生成ID | 锁定 |
| 同实例、足够新版本的账本已显示 | 清理请求关联，按后端操作资格启用 | 按实际资格 |

`industry017.pending.v1`兼容原四字段请求，并在确认后保存本地`confirmation`（status、code、resultVersion、minVersion）。该扩展不发送到HTTP接口。`industry017.view-floor.v1`保存实例及单调版本下限：确认回执、已经显示的新视图均能提高下限；清理请求关联不会清理该下限。响应在应用时重新校验，不按GET发起时的旧状态判断。旧实例和旧版本不得覆盖；页面刷新也遵守同一下限。无resultVersion的STALE_VERSION拒绝至少等待高于原请求版本的视图。

仅在正式账本成功显示后清理关联。确认后的旧实例标记不能通过原“放弃旧请求”入口绕开锁定；该按钮隐藏。服务已关闭时不能恢复其内存账本，应在新标签页使用新启动链接。无待恢复请求时，显式新会话链接允许连接新实例。本段替代原017说明中的前端重启/人工放弃行为描述；后端和授权边界没有改变。

所有故障均为明确标注的合成故障：真实页面、真实HTTP、真实016照管事务；浏览器拦截GET模拟故障或旧响应。拒绝分支另外注入原016测试钩子的提交前故障，未改后端文件。不是实际用户故障记录。

- **确认提交分支8项**：后端根37→38、余额5I→4I；页面旧5I未被当作新账，确认标记先落下。连续失败、业务按钮及隐藏重试按钮的强制事件、期间刷新，业务POST始终只有1次。低于38的视图和其他实例视图被拒绝。读取真实38后才清标记、显示4I及启用NEXT；CARE仍禁用。清标记后晚到37不能覆盖，随后刷新页面仍保留版本下限。完整Core及RNG在照管前后不变。
- **确认拒绝分支5项**：实际提交前失败，完整事务根摘要不变；GET连续失败及刷新时显示拒绝、保留锁定。读取同实例37后才恢复相应按钮。总POST为1，没有自动新请求、错误成功提示或扣费。
- **原浏览器链路10项**：保留原测试所有断言，只把输出路径改到`R1/normal/`。真实12次业务操作完成照管、E8前送、T9恢复；包括原响应丢失、未知结果刷新核对和晚到重试。最终根49、游戏153、步损1→0、RP仍8/12。完整游戏bundle及bundleJSON、工业及人员财务/材料、运输容量与016恢复终态一致；63单位E8结果及RNG在完整游戏比较内。更早永久回执不变。
- 2230个基线文件在验证前后字节不变（仅排除本次修改的app.mjs）。全部验证监听、事务线程、求解进程已关闭，原端口不可连接。

## 复跑与使用

使用原017已准备的`.runtime`，运行前仍由原`INPUTS.json`核验全部依赖。需要原Python环境（NumPy/SciPy）、Node、Playwright和Edge。已有工作区可直接运行：

```powershell
# 在仓库根目录，使用原017具备NumPy/SciPy的Python
python experiments/industry-integrate-017/R1/verify.py
```

`PLAYWRIGHT_MODULE`可指定已有模块路径；默认查找本机Codex附带Playwright。本次使用原准备目录的逐文件SHA256校验副本，没有重跑旧战役或旧验证全套。全新检出缺少私有运行依赖时，先按原017的prepare说明准备依赖；不要运行原`verify.py`覆盖原证据。R1验证器只写本目录和忽略的`.runtime/r1-normal-browser.mjs`，并自动关闭验证服务。

手动本机入口继续使用原命令：

```powershell

# 用终端完整会话链接进入；关闭按Ctrl+C
```
